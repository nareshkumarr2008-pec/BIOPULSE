Why this isn't just another heart-rate alert

"Heart rate high" is not a diagnosis.

Most wearables threshold a single number and push a notification. BioPulse runs a trained clinical model on-device and explains its reasoning — the difference between a smoke alarm and a doctor.

⌚
A typical fitness watch
Threshold-based heart-rate alert
–Compares BPM to one fixed number and fires "Heart rate high" or "Low" — no context on rhythm shape.
–Can't tell AFib, a PVC, or a STEMI pattern apart from someone simply climbing stairs.
–No explanation offered — you get a number and a vague warning, then you're on your own.
–Most models and thresholds are tuned centrally, on whatever population the vendor happened to train on.
–Raw sensor data is commonly synced to the vendor's cloud for any deeper analysis.
◈
BioPulse Pocket Doctor
Explainable on-device diagnosis
✓Classifies the actual rhythm pattern — AFib, STEMI, PVC — from waveform morphology, not a single BPM threshold.
✓Surfaces the exact segment and reasoning behind each call, like the attention heatmap on the Edge AI tab.
✓The model was shaped by federated training across many hospitals' data — without any hospital's records ever moving.
✓Runs inference and explanation entirely on-chip — sub-second, zero network round-trip.
✓Gates out low-confidence noise automatically, so real escalations aren't buried in false alarms.
In one line: a generic watch tells you a number crossed a line. BioPulse tells you what it saw, why it's confident, and routes only the calls that matter to a clinician — without your vitals ever leaving your wrist.

System Architecture

From raw signal to
trusted decision.

Three stacked layers turn a messy, disconnected hospital record into a real-time, explainable alert — without a single patient chart ever leaving the building it was created in.

Layer 1
Standardize
Raw FASTQ reads, HL7 v2 messages and lab CSVs are parsed and validated, then merged into one HL7 FHIR resource — a common language every downstream system can read.
→
Layer 2
Federate
Only encrypted model weights travel between hospital nodes and the global model. Patient records never move — accuracy improves, privacy doesn't erode.
→
Layer 3
Infer, Explain
The trained model ships to a TinyML chip on the wearable. Inference and explanation both happen on-device, in under a second, with zero cloud dependency.
On-chip TinyML inferenceRuns the trained model locally — no network call, sub-second response.
Low-power batteryOptimized for always-on monitoring across multi-day wear.
ECG sensor arraySkin-contact electrodes stream raw waveform into the chip.
Radio disabled by defaultNo outbound connection needed for detection or explanation.

    Proposed methodology
    
      
    Training data: public arrhythmia corpora (MIT-BIH Arrhythmia Database, PTB-XL) as pretraining, then federated fine-tuning across partner-hospital cohorts with informed patient consent.
    
      
    Split: patient-level (not record-level) train/validation/test split to prevent leakage between a patient's beats appearing in both training and test sets.
    
      
    External validation: a held-out hospital site never included in federated rounds, to test generalization before any deployment claim.
    
      
    Clinical sign-off: cardiologist-adjudicated labels as ground truth, with inter-rater agreement (Cohen's κ) reported alongside model accuracy.
    
    
    

    
    
      
    Known limitations — stated plainly
    
      
    This prototype's ECG waveforms are synthetically generated, not real patient signal — the numbers above are illustrative targets, not measured clinical performance.
    
      
    No prospective clinical trial has been run. Sensitivity/specificity claims require an IRB-approved study before any deployment or regulatory submission.
    
      
    Federated training can still inherit bias if participating hospitals are not demographically diverse — this needs active auditing, not an assumption of fairness.
    
      
    On-device inference reduces latency but constrains model size — there is a real accuracy/efficiency trade-off we'd need to characterize per hardware target.

    Deployment & Impact
    
    Designed for clinics
    with no reliable internet.
    
    
    Federated learning and on-device inference aren't just privacy features — they're what make BioPulse deployable in exactly the settings that need it most: low-connectivity regions where cloud-dependent tools fail first.

    People globally with limited access to a cardiologist (WHO estimate range)

    Marginal connectivity cost per on-device inference
    
      
    4
    Planned pilot regions across three continents
    
      
    SMS
    Fallback escalation channel where data networks don't reach
    
    
    

    
    
      
    
        
    Phase 1
    
        
    Pilot
    
        
    3–5 partner clinics, IRB-approved data collection, prospective validation against cardiologist-adjudicated labels.
    
      
    
      
    →
    
      
    
        
    Phase 2
    
        
    Regulatory Pathway
    
        
    Pursue FDA SaMD (Class II, 510(k)) and CE marking in parallel with local approvals in pilot countries.
    
      
    
      
    →
    
      
    
        
    Phase 3
    
        
    Regional Scale
    
        
    Federated onboarding of new hospital nodes — each joins the global model without shipping a single record elsewhere.
    
      
    
      
    →
    
      
    
        
    Phase 4
    
        
    Sustained Operation
    
        
    Low-power hardware and zero required connectivity keep operating cost near-flat as the network grows.
    
      
    
    
    

    
    
      
    Governance & consent model
    
      
    Data stays local: each hospital node retains full custody of its records; only encrypted model weights leave the building.
    
      
    Patient consent: opt-in enrollment with a plain-language consent flow, and an opt-out that removes a patient's device from future federated rounds.
    
      
    Low-connectivity fallback: when a data network is unavailable, a critical alert can degrade gracefully to an SMS-based escalation to a designated clinician contact.
    
      
    Cost model: device cost is one-time and low-power; there is no recurring cloud inference bill since scoring happens on-chip.
